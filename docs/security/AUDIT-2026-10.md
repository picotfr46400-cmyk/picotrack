# PicoTrack — audit sécurité du 3 octobre 2026

Révision auditée : `c78a33d` (identique sur `main` et `v2` au moment de l’audit).
Périmètre : code applicatif (routes `/api`, bundle client, `vercel.json`). Pas de modification des variables Vercel ni des projets Supabase.
Référentiels : OWASP ASVS 5.0 Level 2 (application), OWASP Top 10:2025, OWASP API Security Top 10:2023, RGPD art. 25 et 32. Cartographie ISO/IEC 27001:2022 Annexe A et SOC 2 limitée au produit (ces deux référentiels certifient une organisation).

Les numéros de ligne cités sont ceux de `c78a33d`, avant les correctifs de cette branche.

## Alerte production

Deux failles **critiques sont dans le code actuellement déployé** (`main` = `c78a33d`, client live `efc.picotrack.fr`). Elles exigent un compte déjà authentifié sur ce client. Elles ne demandent pas de changer les variables d’environnement ni le projet Supabase.

1. **Usurpation d’identité sur `/api/function`.** `getRequestUserProfile` (`api/function.js`, environ l. 334-360) prenait l’acteur dans `x-pt-user-id` ou `x-pt-user-email` dès que l’en-tête était présent, et ne vérifiait le JWT que si ces en-têtes étaient absents. Un utilisateur connecté pouvait donc faire exécuter les actions d’administration (création, modification, suppression d’utilisateurs, quotas) avec le profil d’un autre compte du même projet Supabase, y compris un administrateur plateforme.
2. **Élévation et fuite de secrets via `/api/records`.** Après un simple JWT, `handleSave` / `handleList` (`api/records.js`, entités dès l. 4, colonnes `password_hash` et `supa_key` vers l. 127-129, écriture vers l. 420) écrivent et relisent avec la clé service. Un utilisateur connecté pouvait modifier `role` et `resolved_permissions` (devenir administrateur plateforme), lire les empreintes PAD (`password_hash`, SHA-256 non salé, réutilisables telles quelles sur `/api/pad-auth`) et, si la colonne est remplie, `tenants.supa_key`.

Correctif minimal pour `main` (ne pas merger cette branche dans `main`) : le même changement que ici sur `api/function.js` (identité = JWT uniquement, liste blanche des fonctions) et `api/records.js` (retrait des colonnes secrètes, refus d’élever un rôle plateforme, filtre `environment_code` sur PATCH/DELETE). Aucune variable d’environnement, aucune migration.

**Non exploitable sur Vercel aujourd’hui :** l’héritage des clés EFC via un hôte `localhost.evil.com`. Le 3 octobre 2026, `GET https://efc.picotrack.fr/api/bootstrap` avec `X-Forwarded-Host: localhost.evil.com` répond toujours `host: efc.picotrack.fr`. Un `Host: localhost.evil.com` reçoit `DEPLOYMENT_NOT_FOUND` (Vercel route sur le vrai hôte et réécrit `X-Forwarded-Host`, documenté comme identique à `Host`). Le défaut de code est réel et corrigé quand même : il ne doit pas dépendre de ce comportement de plateforme.

## Méthode

Lecture de toutes les routes `/api`, de `_server-supabase.js`, du bundle `assets/app.secured.js`, de `assets/core-supervision.js`, de `public.html`, `pad-mode.js`, `index.html`, `vercel.json`. Contrôle des en-têtes sur la réponse live de `/api/bootstrap`. `npm test` (36 tests). `npm audit` impossible : pas de `package-lock.json` et `dependencies` est vide. Pas de test d’intrusion authentifié contre la production (pas d’identifiants, et les deux critiques n’ont pas besoin d’être rejouées pour être confirmées dans le code).

## Constats

### Critique

#### C1 — Usurpation du profil sur `/api/function`

- **Où :** `api/function.js` `getRequestUserProfile`, l. 334-360 (`c78a33d`).
- **Scénario :** un JWT valide quelconque suffit. L’en-tête d’identité remplaçait l’utilisateur du jeton pour `create-user`, `update-user`, `delete-user`, `update-license-limits`. Le contrôle `requireAuth` ne couvrait que « quelqu’un est connecté », pas « c’est bien cet utilisateur ».
- **Référentiels :** ASVS V8, Top 10 A01, API1 / API5, RGPD art. 32, ISO A.5.15 / A.8.3.
- **Correctif :** l’acteur vient uniquement de `getAuthUser` (JWT vérifié auprès de Supabase). Les en-têtes `x-pt-user-*` sont ignorés. Un non-plateforme ne peut plus attribuer `super_admin`, `platform_admin`, `scope=platform` ni `resolved_permissions.platform_admin`.

#### C2 — Écriture service-role et colonnes secrètes sur `/api/records`

- **Où :** `api/records.js` l. 4-8, 121-129, 377-483 (`c78a33d`).
- **Scénario :** tout utilisateur du tenant lit `user_profiles`, `licenses`, `tenants` en `select=*` et réécrit une ligne par id, sans filtre d’environnement sur le PATCH. Conséquences : élévation de rôle, vol d’empreintes PAD, lecture d’une clé Supabase stockée dans `tenants.supa_key` si elle existe. Le client officiel ne lit pas ces colonnes ; l’API les renvoyait quand même. Les empreintes PAD sont le secret lui-même (`/api/pad-auth` compare l’empreinte envoyée par le navigateur).
- **Correctif :** `password_hash`, `supa_key`, `supa_url` ne sont plus écrits ni renvoyés. PATCH/DELETE hors plateforme sont limités à l’`environment_code` du profil. `tenants` est réservé au profil plateforme. `licenses` et l’écriture de `user_profiles` / `app_roles` exigent le même périmètre que l’écran Utilisateurs (compte supervision). Un non-plateforme ne peut pas poser un rôle plateforme. Un profil sans `environment_code` ne choisit plus l’environnement demandé : il est cantonné à `DEMO`.

### Haute

#### H1 — Proxy ouvert vers les Edge Functions

- **Où :** `api/function.js` l. 718-736.
- **Scénario :** après authentification, n’importe quel nom de fonction était relayé vers `/functions/v1/{nom}` avec le JWT de l’appelant.
- **Correctif :** seules les actions métier codées dans le fichier, plus `pad-sync` (seul appel hors liste encore présent dans le bundle), sont acceptées. Le reste répond 404.

#### H2 — `/api/auth` peut tenir jusqu’au plafond de 20 s (504)

- **Où :** `api/_server-supabase.js` `readJsonBody` l. 149 ; `fetch` sans délai dans `serviceRest` et dans `api/auth.js` l. 75 ; `vercel.json` `maxDuration: 20`.
- **Cause dans la fonction :** si `req.body` n’est pas déjà parsé, le handler attend l’événement `end` du flux sans délai. Sur Vercel ce corps est parfois pré-parsé (réponse 200 rapide) et parfois un flux qui n’émet jamais `end` : l’isolate est tué au plafond de 20 s (504). La base n’est pas en cause dans ce chemin, elle n’est même pas appelée. Les appels Supabase suivants n’avaient pas non plus de délai : une connexion bloquée produisait le même 504.
- **Correctif :** lecture du corps bornée à 2,5 s (408), `AbortSignal` de 8 s sur l’échange de mot de passe et de 15 s sur le REST métier. Un utilisateur qui se connecte normalement ne voit pas de changement. Ce n’est pas un allongement de `maxDuration`.

#### H3 — `startsWith('localhost.')` et confiance dans `X-Forwarded-Host`

- **Où :** `api/_server-supabase.js` l. 6, 40, 61-64, 85-89.
- **Scénario si l’en-tête était honoré :** `localhost.evil.com` et `127.0.0.1.evil.com` passaient pour un poste local, donc héritaient du repli `SUPABASE_*` (projet EFC) et court-circuitaient le refus « pas de fuite EFC ». L’hôte canonique `efc.picotrack.fr` n’était pas épinglé sur le ref `jcanufkmcslxwmheqccp` : toute URL mise dans `EFC_SUPABASE_*` ou le repli était acceptée.
- **Constat live :** non exploitable sur Vercel le 3 octobre 2026 (voir l’alerte). Corrigé malgré tout : hôte local = égalité stricte (`localhost`, `127.0.0.1`, `0.0.0.0`, `::1`) ; si `X-Forwarded-Host` diffère de `Host`, `Host` gagne ; `efc.picotrack.fr` n’accepte que le ref connu.

#### H4 — Empreinte PAD non salée, utilisée comme secret

- **Où :** `assets/app.secured.js` `hashPassword` (SHA-256 du mot de passe) ; `api/pad-auth.js` l. 12-22.
- **Scénario :** l’empreinte transite et, avant C2, était lisible via `/api/records`. Elle suffit à ouvrir une session PAD. Pas de délai anti-force brute.
- **Correctif compatible :** la comparaison n’accepte plus qu’une empreinte hex de 64 caractères (ce que le client envoie déjà) ; 8 échecs / 10 min / IP+identifiant. **Résidu (moyen) :** le protocole reste « l’empreinte est le secret ». Passer à un mot de passe vérifié et salé côté serveur changerait le client PAD : hors de ce lot. Les empreintes déjà divulguées restent valides tant qu’elles ne sont pas régénérées.

#### H5 — HTML arbitraire dans les e-mails Resend

- **Où :** `api/send-mail.js` l. 26 et gabarit l. 11. Le bundle appelle `/api/send-mail` (pas `api.resend.com`). Aucune clé `re_…` dans le bundle. `CSP` autorisait quand même `connect-src https://api.resend.com`.
- **Scénario :** un JWT valide envoyait `html` tel quel, servi depuis l’adresse PicoTrack. Les déclencheurs passent `html` s’il est configuré sur le formulaire.
- **Correctif :** suppression des balises `script` / `iframe` / `object` / `embed` / `form` et des `javascript:` / gestionnaires `on*`. Le texte simple et le HTML de mise en forme restent. `api.resend.com` est retiré du `connect-src` (les envois passent par `/api/send-mail`). **Résidu :** ce n’est pas un parseur HTML complet.

#### H6 — Rejeu DNS sur les webhooks

- **Où :** `api/_webhook-url.js` : contrôle DNS, puis `fetch` qui résout une seconde fois (`api/_integrations.js` `dispatchWebhook`).
- **Scénario :** entre les deux résolutions, le nom peut pointer vers une adresse privée (rejeu DNS). Les plages privées, le metadata et les ports exotiques étaient déjà refusés.
- **Correctif :** la connexion TCP/TLS vise l’adresse qui vient d’être contrôlée (`servername` conservé pour le certificat). Les redirections ne sont pas suivies.

#### H7 — En-têtes navigateur incomplets, scripts CDN sans SRI

- **Où :** `vercel.json` l. 63-80 (pas de HSTS ni `X-Frame-Options` sur les pages ; `script-src 'unsafe-inline'` ; `connect-src` Resend). `index.html` : React et ReactDOM sans `integrity`, plus `@babel/standalone` alors que le bundle n’appelle pas Babel. L’API posait déjà HSTS (vu sur la réponse live).
- **Correctif :** HSTS et `X-Frame-Options: DENY` sur les pages ; SRI sha384 de React 18.3.1 et ReactDOM ; suppression de Babel. **`unsafe-inline` est conservé** : le bundle et `index.html` dépendent de scripts inline. Le retirer casserait l’application. Voir M1.

### Basse

- `security.txt` pointe vers une politique qui peut être absente ; expiration 2027.
- `GET /api/send-mail` répond sans authentification (statut du endpoint seulement).
- `api_records.js` et `app.secured-v45.js` à la racine ne sont pas publiés par `build.js`.
- Politique de mot de passe : 8 caractères, pas de MFA (ASVS L2 authentification forte : partiel).
- `signOut` et les suppressions avalent certaines erreurs Supabase (`.catch`).
- CORS `*` seulement lorsqu’il n’y a pas d’en-tête `Origin` (appels hors navigateur).
- Jeton de session appareil comparé en clair en base.
- Secret HMAC PAD : `_pad-security.js` retombe sur la clé service si `PAD_SESSION_SECRET` est vide. Ne pas changer ce repli sans poser la variable, sinon les tablettes déjà connectées cassent. Action d’exploitation : définir `PAD_SESSION_SECRET` (processus, pas ce PR).
